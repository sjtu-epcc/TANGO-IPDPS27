Online large language model (LLM)~\cite{vaswani2017attention,brown2020language} services consolidate requests from different applications~\cite{lin2024parrot} on shared model instances to improve GPU utilization and reduce costs~\cite{yu2022orca,kwon2023vllm}.
These applications impose distinct latency requirements~\cite{sun2024llumnix,goel2026qoserve,zhang2026jitserve}.
For example, interactive chat prioritizes fast first token generation~\cite{goel2026qoserve}, while real-time translation~\cite{zhang2026jitserve} requires short latency between consecutive output tokens.
% These applications impose distinct performance requirements.
% Some requests are sensitive to the latency before the first output token, as in interactive chat, whereas others are sensitive to the latency between consecutive output tokens, as in real-time translation.
These latency requirements correspond to two phases of LLM inference. During \emph{prefill}, model processes prompt and generates the first output token, measured by the time to first token (TTFT).
During autoregressive \emph{decode}, it generates subsequent tokens one at a time, measured by the time per output token (TPOT)~\cite{agrawal2024sarathi,zhong2024distserve}.
These two phases can execute on disaggregated GPU pools or colocate on the same GPUs~\cite{patel2024splitwise,qin2025mooncake,agrawal2024sarathi}.
% Online serving systems should therefore improve the goodput while meeting the application-specific TTFT and TPOT Service-Level Objectives (SLOs).


Facing such a scenario, LLM serving should \textit{improve the goodput while meeting the TTFT and TPOT Service-Level Objectives (SLOs)} for requests with heterogeneous latency requirements.
Disaggregated deployment partitions GPU resources by phase, which can leave one pool underutilized while urgent requests queue in the other~\cite{ruan2026libra,wu2024loongserve}, as the phase-specific demand of tight-SLO requests changes over time.
Thus, representative Multi-SLO systems like SOLA~\cite{hong2025sola} and JITServe~\cite{zhang2026jitserve} typically adopt colocation, allowing prefill and decode requests to share GPU resources flexibly and improving goodput.
Under colocation, these systems combine continuous batching~\cite{yu2022orca}, which dynamically admits new requests into the active batch between iterations, with chunked prefill~\cite{agrawal2024sarathi}, which divides long prompts into smaller segments that can be processed alongside decoding requests.
Both techniques are adopted by state-of-the-art LLM serving engines such as vLLM~\cite{kwon2023vllm} and SGLang~\cite{zheng2024sglang}.
% Disaggregation partitions GPU resources by phase, limiting fine-grained resource sharing between phases.
% Under heterogeneous SLOs, urgent work in one phase may remain queued despite spare capacity in the other, since using that capacity requires reallocating resources between the two pools.
% In contrast, representative SLO-aware systems such as SOLA and JITServe adopt colocation to flexibly share resources and improve goodput.

For the requests in the waiting queue, at each execution step, \emph{temporal scheduling} first determines which waiting requests to dispatch for execution alongside ongoing requests.
Then, \emph{spatial scheduling} allocates the step's token budget among these requests to form a batch, specifying the sizes of prefill chunks and the number of decode tokens to include.
At last, the engine executes the batch, updates request states, and repeats this process for the next step.
% We abstract this process into two coupled scheduling dimensions: \emph{temporal scheduling}, which determines request execution priority and admission, and \emph{spatial scheduling}, which determines token allocation within each batch.
The temporal and spatial scheduling jointly shape request queueing and step duration, affecting TTFT and TPOT.

Existing goodput-oriented serving engines commonly use first-come-first-served (FCFS) admission for temporal scheduling~\cite{kwon2023vllm} and a fixed maximum token budget for spatial scheduling, without appropriate adaptations to the heterogeneous SLOs of requests.

The low SLO attainment stems from the inefficiencies in both the temporal and spatial scheduling aspects.


As for the temporal aspect,
SLO-unaware request dispatching leads to an admission order that does not reflect request urgency.
Under FCFS, a request with a tight TTFT objective can wait behind earlier requests with ample latency slack~\cite{patke2024qlm}.
The urgent request may exhaust its TTFT budget in the queue, even though the earlier requests could tolerate being served later.
FCFS therefore misses the opportunity to defer less urgent requests and use their slack to reduce queueing delays for requests with tighter SLOs.


As for the spatial aspect, 
existing works allocate tokens under a fixed per-step budget without considering the TPOT requirements of active decode requests.
% Because decoding requests must wait for the entire batch to finish before receiving their next tokens, admitting more prefill work can prolong their inter-token delays.
However, we observe that the step time depends on both the total token count in a token batch and the prefill/decode composition.
With 2,048 decode tokens fixed under Qwen3-14B model and RTX 6000 Ada GPU, adding 2,048 prefill tokens increases mean step time from 328.7\,ms to 758.6\,ms.
Even with the total token count fixed at 4,096, pure-prefill, pure-decode, and evenly mixed batches take 610.5\,ms, 682.5\,ms, and 758.6\,ms, respectively.
A fixed token budget alone therefore cannot reliably control step time to meet the TPOT demands of active decode requests.

To address these two inefficiencies, an appropriate solution is to coordinate request-level urgency at the temporal perspective, with batch-level execution time at the spatial perspective.
% Addressing these inefficiencies requires coordinating request-level urgency with batch-level execution time.
However, two challenges still exist to achieve this solution.

% First, temporal scheduling needs to decide which waiting requests to admit and which ongoing requests to defer under resource contention.
First, temporal scheduling should coordinate request dispatching and preemption, deciding which waiting requests to admit and which ongoing requests to defer under resource contention.
These requests have different active SLOs and remaining latency budgets, thus ordering them requires a consistent comparison of urgency in the prefill and decode phases.
Second, spatial scheduling should balance prefill and decode latency requirements through per-step token allocation in a mixed token batch.
More prefill token allocation advances urgent TTFT requests but delays decode requests, while fewer prefill tokens have the opposite effect.
%  whereas overly restricting prefill can leave those urgent requests waiting.
This tradeoff requires accurate step-time estimates for different prefill/decode compositions and context lengths to guide the token allocation.


We therefore propose \tango{}, a multi-SLO LLM serving system that jointly controls temporal request dispatching and spatial token allocation.
\tango{} aims to improve the goodput while satisfying heterogeneous TTFT and TPOT SLO requirements of requests.
It comprises a \dispatcher{} and a \allocator{}.
The \dispatcher{} assigns phase-aware latency deadlines according to each request's active SLO and uses them to guide admission and preemption, prioritizing requests with tighter latency budgets.
The \allocator{} uses a step-time model to estimate the execution time of mixed prefill/decode batches, and adjusts their prefill token budgets according to the remaining latency slack of decoding requests.

This paper makes three major contributions:
\begin{itemize}
  \item \textbf{Investigating the scheduling inefficiencies of current multi-SLO LLM serving.}
  The analysis motivates us to account for heterogeneous request urgency and mixed prefill/decode interference through joint control of temporal request dispatching and spatial token allocation.
  %  from temporal and spatial perspectives.

  \item \textbf{The design of a \dispatcher{} that prioritizes requests across LLM prefill and decode phases.}
  By mapping each request's active SLO to a comparable deadline, it guides request admission and preemption, mitigating temporal inefficiency caused by SLO-unaware queueing.

  \item \textbf{The design of a \allocator{} that adapts token batch composition to latency constraints.}
  Based on predicted step time, it converts the remaining TPOT slack into a prefill token budget, mitigating spatial mixed prefill/decode interference while preserving progress for requests with tight TTFT SLOs.
\end{itemize}


We evaluate \tango{} against state-of-the-art LLM serving systems, including vLLM~\cite{kwon2023vllm}, SOLA~\cite{hong2025sola}, and JITServe~\cite{zhang2026jitserve}, using Llama-3.1-8B~\cite{grattafiori2024llama3}, Qwen3-14B~\cite{yang2025qwen3}, Qwen3-32B~\cite{yang2025qwen3}, Llama-3.1-70B~\cite{grattafiori2024llama3}, and Qwen3-Next-80B-A3B-Instruct~\cite{qwen2025next} under chatbot, mathematical-reasoning, and software-agent workloads.
Compared to the baselines, \tango{} improves the overall SLO attainment by 58.72\% and improves the goodput by 1.52$\times$ on average.
