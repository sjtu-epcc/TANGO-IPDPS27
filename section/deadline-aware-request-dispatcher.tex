\section{\dispatcher{}}
\label{sec:deadline-aware-request-dispatcher}

The dispatcher determines which waiting requests to admit and which running requests should yield memory when KV-cache capacity is exhausted.
Our key idea is to coordinate these decisions through phase-aware deadlines: earlier deadlines receive higher admission priority, while later deadlines identify candidates for preemption.

\subsection{Phase-Aware Request Ordering}
\label{subsec:phase-aware-request-ordering}

As analyzed in Section~\ref{subsec:motivation-underlying-reasons}, arrival order does not reflect request urgency under heterogeneous SLOs.
The active objective also changes as inference progresses: a request must first produce its initial token within the TTFT budget, and then sustain token generation within the TPOT budget.
We express both objectives as a deadline for the next required output, as illustrated in Fig.~\ref{fig:phase-aware-deadlines}.
Let $q_i$ denote the number of output tokens already returned by request $r_i$.
Using the timestamps and SLOs defined in Section~\ref{sec:multi-slo-llm-serving}, its deadline is
\begin{equation}
  D_i =
  \begin{cases}
    a_i + S_i^{\mathrm{TTFT}}, & q_i = 0, \\
    t_{i,q_i} + S_i^{\mathrm{TPOT}}, & q_i > 0.
  \end{cases}
  \label{eq:phase-aware-deadline}
\end{equation}
where $t_{i,q_i}$ is the latest output timestamp, denoted by $t_{\mathrm{last}}$ in Fig.~\ref{fig:phase-aware-deadlines}.

Before the first token, the deadline is fixed by the arrival time and TTFT SLO.
Chunked prefill splits the execution across iterations, but all chunks contribute to the same first-token latency and therefore share this deadline.
For $r_1$ in Fig.~\ref{fig:phase-aware-deadlines}, arrival at $0$~ms and a TTFT SLO of $180$~ms give $D_1=180$~ms throughout prefill.
Both queueing and chunk execution consume this budget; scheduling another chunk does not renew it.

Once the first token is returned, the deadline advances with output progress.
Each returned token establishes the next target by adding the TPOT SLO to its timestamp.
For $r_3$ in Fig.~\ref{fig:phase-aware-deadlines}, a TPOT SLO of $100$~ms and an output timestamp advancing from $0$ to $20$~ms move the deadline from $100$ to $120$~ms.
These rolling deadlines translate the TPOT objective into per-token targets; meeting them is sufficient to satisfy the average-TPOT objective in Section~\ref{sec:multi-slo-llm-serving}.

At each iteration boundary, the dispatcher sorts waiting requests by increasing $D_i$ and considers them for admission in order.
Ties are broken by arrival time and then request identifier.
This order gives earlier service to requests whose next output is due sooner, subject to the engine's sequence and memory limits and the allocator's token budget.


\subsection{Deadline-Aware Preemption}
\label{subsec:deadline-aware-preemption}

\begin{figure}[t]
  \centering
  \includegraphics[width=\columnwidth]{figures/tango-methodology/deadline-admission-preemption.pdf}
  \caption{Deadline-aware admission and preemption (times in ms).}
  \label{fig:deadline-admission-preemption}
  \vspace{-3mm}
\end{figure}

Waiting-queue ordering alone is insufficient when running requests occupy the available KV-cache memory~\cite{gong2025pastfuture}.
In Fig.~\ref{fig:deadline-admission-preemption}, $r_4$ is first in the waiting queue but cannot be admitted while requests with later deadlines retain their KV-cache blocks.
We therefore extend deadline priority to memory reclamation.
When KV allocation for a waiting request $r_j$ fails, the dispatcher selects the running request with the latest deadline as the candidate victim $r_v$, choosing the later-arriving request when deadlines are equal.

The comparison in Fig.~\ref{fig:deadline-admission-preemption} permits preemption only if $D_j < D_v$.
Thus, memory is reclaimed from a request whose next output is due later; if no running request has a later deadline, $r_j$ remains queued.
When preemption is permitted, the engine reclaims the victim's KV-cache blocks at the iteration boundary, returns it to the queue, and retries allocation for $r_j$.
Admission proceeds once allocation succeeds.

Preemption preserves the victim's arrival time, SLOs, output-token count, and latest output timestamp.
Consequently, Eq.~\ref{eq:phase-aware-deadline} gives it the same deadline upon requeueing: the original TTFT deadline before the first token, or the existing next-token deadline afterward.
Time spent waiting for resumption continues to consume its latency budget.

For the example in Fig.~\ref{fig:deadline-admission-preemption}, $r_4$ ($D_4=60$~ms) precedes $r_5$ ($D_5=200$~ms), while $r_1$ has the latest running deadline of $180$~ms.
Since $60<180$, the dispatcher preempts $r_1$ and admits $r_4$ after retrying KV allocation; $r_2$ and $r_3$ remain running.
The requeued $r_1$ retains its $180$~ms deadline and therefore returns ahead of $r_5$, as shown in the updated waiting queue.
